## Limitations and Evidence Rules

Current status is unverified, not “no defects.” Document real candidate limitations after assessment; do not fabricate issue numbers or claim full accessibility, uptime, backup/recovery or security certification from design completion.

Exact submitted-material integrity, current authority/private delivery and real Git behavior need their matching facilities. A successful frontend build, diagram render or mock response does not establish full release acceptance. Keep failed, blocked and unexecuted checks visible in owning records.

## Publication and Deployment Boundary

Tagging and publishing are future separately authorized actions after release gates pass. Publish the notes from the exact verified tag. Record rollout separately: a published release need not be deployed, and a configured host is not evidence of published release identity.

Use the [release/deployment flow](01-Deployment-Plan.md#release-and-deployment-decision-flow) for the decision boundary. If deployment/recovery changes actual operating state, record its outcome without rewriting the tagged release's historical identity or implying an irreversible data effect was undone by code rollback.
